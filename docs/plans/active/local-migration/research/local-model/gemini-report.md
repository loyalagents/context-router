Architecture Decision Report: Local-First AI Runtime and Inference IntegrationExecutive RecommendationThe architectural imperative for a local-first application integrating an on-device inference engine requires balancing execution performance, developer velocity, and long-term maintainability. The core challenge resides in embedding a robust, hardware-accelerated inference environment without saddling the primary TypeScript/Node.js host application with systemic instability or complex deployment paradigms.The primary recommendation is to adopt an out-of-process architecture utilizing a standalone, dynamically spawned llama-server binary, which is the native HTTP server provided by the llama.cpp project. This executable will be supervised and managed by the NestJS backend via standard operating system child-process execution.This approach cleanly separates the three core architectural decisions required for this product. First, regarding the inference engine, llama-server provides the most performant, lowest-overhead execution environment across Apple Silicon, Windows, and Linux operating systems. Second, concerning model weights, the Qwen2.5-7B-Instruct model, quantized to a 4-bit GGUF format, is recommended as the baseline due to its Apache 2.0 license, massive 128,000-token context window, and exceptional capability in structured JSON generation. Third, regarding process ownership, the NestJS application will manage the lifecycle of the inference server natively, decoupling the Model Context Protocol (MCP) server logic from the memory-intensive tensor operations. The deployment strategy will smoothly transition from an initial "manual setup" phase—where the user independently provisions a local server or Ollama instance—to a "managed" end-state where the application downloads the pre-compiled llama-server binary and GGUF model files, executing them invisibly in the background.The strongest counterargument to a standalone llama-server process is native embedding via node-llama-cpp, which provides direct JavaScript/TypeScript bindings to the llama.cpp core. Proponents of node-llama-cpp emphasize its deep runtime integration, automatic model downloading mechanisms, and built-in typed JSON schema parsing without requiring the host application to manage network ports or parse HTTP responses. Furthermore, node-llama-cpp resolves cross-platform compilation automatically during the application's installation phase.However, the evidence favoring out-of-process isolation outweighs the convenience of native bindings. The fatal flaw of native embedding in a Node.js environment is the erosion of process isolation. Heavy machine learning workloads frequently encounter edge-case memory access violations, such as exceeding unified memory limits or triggering segmentation faults during aggressive tensor calculations. In a natively embedded architecture, a fault in the C++ inference engine will catastrophically crash the entire NestJS host application. By running llama-server as a discrete child process, the NestJS application preserves its own stability. It can detect the child process termination, log the error, and attempt a graceful restart of the inference engine without disrupting the Next.js user interface or severing existing MCP connections. Moving forward with an HTTP-based out-of-process architecture secures the application against lower-level hardware faults.Inference Engine Candidate EvaluationThe landscape of local inference engines presents varying philosophies regarding resource overhead, licensing, and integration depth. If a user already has Ollama installed, the application must carefully avoid modifying the user's global model cache or conflicting on default network ports. This strictly disqualifies LM Studio as a foundational dependency for a standalone distributable product, as it introduces severe legal liabilities regarding distribution rights.Apple MLX is a native machine learning framework optimized for zero-copy memory arrays on M-series chips, delivering theoretically higher steady-state throughput than standard C++ engines. While performant, MLX completely abandons cross-platform portability, restricting execution entirely to macOS. Adopting MLX would mandate maintaining a parallel inference architecture for the subsequent Windows and Linux releases, severely violating the stated prioritization of simplicity and maintainability.Security, Local Endpoint Constraints, and Process LifecycleA local-first application exposing an MCP server while simultaneously operating a background HTTP inference engine introduces highly localized threat vectors. The primary concerns revolve around Cross-Site Request Forgery (CSRF), Domain Name System (DNS) rebinding attacks, and improper process lifecycle management.If the llama-server binds to the standard loopback address (127.0.0.1) without authentication, any malicious script executing in the user's web browser can dispatch requests against the local API. While the browser's Same-Origin Policy (SOP) generally prevents the attacker's script from reading responses, simple HTTP POST requests containing JSON-RPC payloads still hit the local network stack and trigger server execution before any Cross-Origin Resource Sharing (CORS) check terminates the transaction. In more advanced DNS rebinding attacks, the browser is tricked into treating a malicious external domain as identical to localhost, granting the attacker full read-write access to the local MCP server without triggering CORS blocks.To mitigate these threats, loopback binding alone is insufficient. The NestJS orchestrator must utilize the --api-key flag supported by llama-server. During initialization, the backend must generate a cryptographically secure, ephemeral token, pass it to the child process via command-line arguments, and subsequently inject it into the Authorization: Bearer header of all internal API calls. Additionally, the MCP server exposed by the NestJS application must enforce strict CORS policies, validating the Origin header against explicit allowlists to prevent unauthorized browser-based interactions.Process lifecycle management presents another distinct engineering challenge. NestJS provides robust application termination hooks, including BeforeApplicationShutdown and OnApplicationShutdown, which respond to OS-level signals like SIGINT and SIGTERM. When the user closes the desktop application, the NestJS orchestrator must explicitly terminate the llama-server child process.A critical vulnerability exists within the llama-server architecture regarding client disconnections. Extensive documentation and bug reports indicate that when an HTTP client disconnects abruptly, the engine fails to halt the ongoing token generation. The orphaned generation continues to occupy inference slots and maximize GPU utilization until the context window is entirely exhausted. Because abandoning an HTTP request does not release the computational resources, the NestJS backend must utilize the dedicated /slots/{id_slot}?action=cancel or equivalent management endpoints to explicitly abort tasks before dropping connections. Failure to implement this specific cleanup protocol will result in severe battery drain and thermal throttling on the user's hardware.Transition Architecture: Manual to Managed StateThe prioritization of a rapid initial release permits a phased integration approach. By establishing a rigid network boundary between the NestJS backend and the inference engine via OpenAI-compatible REST API payloads, the core logic of the application remains entirely insulated from the physical execution context.The initial release will rely on manual setup. The user will be instructed to install a runner manually, such as downloading Ollama or executing a raw llama-server binary, and will configure the application via a simple UI to point to the local port. This phase validates the application's prompt engineering, schema definitions, and internal SQLite data flows without requiring upfront investment in cross-platform binary packaging.The transition to a fully managed background operation requires specific architectural additions while preserving the vast majority of the established codebase. The application's HTTP client layer, which dispatches requests using standard chat completion formats, will remain untouched. The prompts, the complex multi-step orchestration, and the MCP server implementation are completely reusable.The replaced work primarily involves the configuration UI, which will be deprecated or moved to an advanced debugging view, as the application assumes total authority over port assignment and process supervision.Moving to a fully managed state demands the implementation of a secure asset pipeline. The application must download the requisite llama-server binary tailored for the host operating system alongside the chosen .gguf model files. To prevent interfering with a user's existing model runner or cache, these assets must be stored in isolated, application-specific directories, such as ~/Library/Application Support/[AppName]/models on macOS or %APPDATA%\[AppName]\models on Windows. This sandboxing ensures that if the user runs a separate Ollama instance, the application neither corrupts their cache nor suffers from unintended modifications.If the application eventually requires switching from llama-server to an alternative engine, the architectural impact is remarkably constrained. Because the application interacts solely through standardized REST payloads, an engine swap merely requires updating the binary download manifest and adjusting the specific command-line arguments passed to the Node.js child_process. The packaging, supervision, storage, and recovery work remains universally applicable regardless of the underlying engine choice.AI Workloads and Model ShortlistThe specified application workloads transcend the capabilities of standard conversational chatbots, demanding rigorous instruction-following, semantic intelligence, and strict adherence to structured outputs.The task of extracting structured preference suggestions from documents requires the model to identify latent user preferences and map them to discrete categories. Selecting relevant preference categories from a permitted list demands strict constrained decoding to guarantee the model only outputs values recognized by the application's authorization logic. Suggesting the consolidation of overlapping categories requires advanced semantic reasoning to recognize conceptual overlap.The AcroForm filling workload is uniquely structured. The application utilizes a local TypeScript library, such as pdf-lib, to extract field metadata natively, entirely bypassing the need for vision models or native PDF inference. pdf-lib operates completely locally in the browser or Node.js runtime, parsing the AcroForm text fields and checkboxes. The extracted schema is subsequently passed to the language model alongside the user's preferences. The model is tasked solely with returning a structured JSON map that links the preferences to the specific PDF field names.To fulfill these demands, the model must support precise structured output generation. While engines like llama-server enforce syntactic validity via GBNF grammar constraints, they do not alter the underlying semantic probability distribution. If a model struggles with structured reasoning, forcing a grammar mask upon it frequently results in catastrophic degradation, such as infinite repetition loops where the model repeatedly outputs a single token or digit until the maximum token limit is reached. This phase tackles the infrastructure required to dynamically download the platform-specific llama-server binaries and .gguf weights, securely storing them in isolated application directories. Concurrently, standardizing the internal communication over the OpenAI-compatible REST API specification is imperative to ensure future interoperability. The ratification of Qwen2.5-7B-Instruct as the primary evaluation target allows prompt engineering to commence immediately. Conversely, complex binary packaging strategies, the intricacies of Windows driver fallbacks, and any mechanisms for cloud-hosted inference sync can be safely deferred until the core macOS architecture achieves stability.
