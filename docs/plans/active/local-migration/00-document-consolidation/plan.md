## Contracts And Compatibility

- Application/use-case, storage, identity, model, GraphQL, REST, and MCP
  contracts: preserved; this PR does not touch runtime files.
- Configuration and filesystem contract: one dependency-free checker scans
  existing tracked and non-ignored untracked working-tree Markdown files using
  NUL-delimited Git discovery. Staged/unstaged deletions are skipped; renamed or
  new Markdown sources are checked; ignored output is excluded. Unexpected
  discovery/read errors fail closed.
- Checker behavior: local relative targets must exist; fragment-only and remote
  URL targets are ignored; in-repo files and directories are valid; `file:`,
  home-relative, POSIX absolute, Windows-drive, and UNC filesystem targets are
  violations even when they exist locally.
- Decoded/normalized targets may not escape the Git top level. Source symlinks
  and target symlinks that resolve outside it are rejected, and exact path case
  is checked for Linux portability. Percent-decoded filesystem forms and Unicode
  control/format characters are classified before resolution. CommonMark
  backslash escapes are normalized first; character-reference syntax in local
  targets is rejected as unsupported encoding rather than resolved ambiguously.
- Checker output identifies a repository-relative source, line, redacted target
  kind or safe repository-relative target, and reason. It never prints cwd,
  home, a resolved external path, or raw external target text.
- Strict mode exits nonzero on any finding. Baseline mode exits nonzero on any
  finding whose source/reason/hash occurrence cannot consume a matching reviewed
  baseline occurrence; resolving a baseline finding is allowed. The exact-schema
  baseline is pinned to the approved base commit and its entries must regenerate
  from legacy sources at that commit. Baseline entries are restricted to
  base-independent lexical reasons, preventing current filesystem state from
  validating an old missing, case-mismatched, escaping, or source-path finding.
  Invalid CLI, Git/read/parser failures, malformed/tampered baseline data, and
  internal errors remain nonzero in every mode.
- No public or external consumer contract changes.

## Design

### Inventory evidence

Generate the source list directly from the immutable base commit:

```sh
git ls-tree -r --name-only c284ce3f07bc5414edf0ccc1e68d51a8e10a2013 -- docs/plans \
  | rg '\.md$' \
  | rg -v '^docs/plans/active/local-migration/'
```

Agents receive disjoint path groups and return structured recommendations; they
do not edit the branch. Each group is then reviewed by an agent who did not
produce its initial classification. `/root` reconciles findings and is the only
writer of `inventory.md`.

Each row separates four kinds of evidence:

- `Base-document evidence` cites a heading/line or concise content claim from the
  immutable base-commit blob.
- `Durable information or open work` states exactly what must survive, or `None`.
- `Current verification and rationale` cites current code/tests/canonical docs
  when claiming shipped, superseded, or duplicate work and explains the chosen
  disposition. Abandoned brainstorming may instead explain why it contains no
  adopted decision or live work.
- Destination fields name the exact 00B landing point and owner.

A `REHOME_ACTIVE` destination and a `CURRENT`, `USEFUL`, or `PACKAGE_DOCS`
distillation destination may be a precise proposed path that PR 00B will create;
it must exist before source deletion. A `MIGRATION_CONTROL` destination must
already exist with an exact section. If no safe destination can be named, the
source remains active. Any material reconciliation after review resets that row
to `Pending`.

The inventory validator parses the single-line Markdown table with backslash-
escaped pipe characters. It compares the row path set—not merely its count—to
the separately pinned SHA-derived source set and count, enforces bytewise path
order, checks uniqueness and allowed vocabulary/pairs, validates canonical safe
destination paths and real migration-control heading anchors, validates required
fields and KEEP_ACTIVE metadata, proves initial analyst and reviewer differ, and
verifies all 88 legacy blobs remain unchanged from base. A shallow checkout that
lacks the pinned commit fails operationally rather than trusting inventory text.

### Link checker

The checker uses Node.js built-ins and `execFile` Git calls, never a shell. It
validates inline links, images, URI autolinks, and reference definitions while
ignoring fenced and inline code, including container fences and multiline code
spans. Its parser supports nested/escaped labels, balanced/escaped parentheses,
optional titles, angle-bracket destinations with spaces, query/fragment
stripping, percent decoding, and collapsed references. URI autolinks are parsed
so prohibited `file:` targets cannot bypass the filesystem rules; other remote
schemes are not fetched or checked. Undefined reference syntax and raw HTML
links are explicitly outside the local-target check because Markdown does not
resolve the former and this repository does not use the latter as its docs link
convention. Heading fragments are not checked.

The initial strict run is expected to fail on pre-existing violations. The
reviewed temporary baseline stores stable hashes plus source/reason/count
metadata without raw external paths. Baseline mode fails for any new or mutated
finding and for every operational error. It accepts only base-independent lexical
reasons; filesystem-dependent findings can never enter the baseline. The 00A
baseline records 27 POSIX-absolute targets across two unchanged legacy sources.
Later PRs remove violations by carrying out approved inventory dispositions,
not by adding baseline entries.

### Checkpoint 2: Validation tooling and baseline

- Write tests first for both validators.
- Link-checker tests cover valid files/directories, images and reference
  definitions, optional titles, angle/space targets, balanced/escaped
  parentheses and nested/escaped labels, query/fragment and percent handling,
  inline/container-fenced code, undefined/collapsed references, ignored remote

  POSIX/home/Windows/UNC/file absolute forms (including encoded forms), control

  deterministic one-line redacted diagnostics, unknown flags, operational
  failures, strict failure, and baseline schema/pinning/multiplicity/tamper
  behavior.
- Inventory-validator tests cover Markdown pipe escaping, exact SHA path-set
  equality and pinned count, bytewise order, uniqueness, vocabulary and
  compatibility, safe destinations and heading anchors, required evidence,
  KEEP_ACTIVE metadata, analyst/reviewer independence, pending rows, unchanged
  legacy blobs, required CLI arguments, and shallow-history failure.
- Implement the smallest dependency-free validators that pass those tests.
- Run the link checker strictly, inspect findings, and check in a reviewed
  hash-based baseline whose sources are unchanged legacy documents.
- Checkpoint result: validator tests pass; strict mode exposes cleanup work;
  baseline mode passes only because every finding is reviewed and pre-existing.

  reviewer presence.
- Checkpoint result: every base path has exactly one independently approved row;
  no legacy source file changed.

## Privacy And Security

This PR does not read user data, change credentials, open a listener, or make a
remote model/service call. The checker operates only on repository paths and
file contents. Diagnostics must remain repository-relative and must not echo the
reviewer's home directory. Rejecting absolute local links prevents committing
machine-specific filesystem details as navigable documentation.

## Rollback Or Recovery

The PR contains only additive planning/tooling changes plus metadata updates.
Before merge, abandon the branch. After merge, revert the PR normally. No
database, user data, environment, generated output, or hosted deployment state
is affected. The 88 legacy source files remain untouched.

## Risks And Open Questions

- Classification is judgment-heavy. Mitigation: disjoint initial analysis,
  rotated independent review, exact evidence, and `/root` reconciliation.
- Old implementation summaries may be inaccurate. Mitigation: verify only facts
  proposed for preservation; avoid turning PR 00A into Step 01's contract audit.
- A future step directory may not yet exist. Mitigation: require an existing
  migration-control anchor or keep/rehome the active source.
- The checker may surface many historical absolute links. Mitigation: report all
  deterministically in 00A and remove them through approved 00B/00C work rather
  than weakening the rule.
- PR 00B topic splits could race with Step 01. Mitigation: 00A records exact
  destinations and later branch owners declare exclusive paths before editing.
